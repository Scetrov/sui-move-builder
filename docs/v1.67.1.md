# Sui 1.67.1 Upgrade Notes

## Status

This document summarizes the attempted upgrade of `sui-move-builder` from the previous Sui `1.63.3` baseline to Sui `1.67.1`, the issues found during verification, and the remediation plan required to reach a fully working and verified release.

Implementation has now started on the active branch. The branch pins Sui `1.67.1`, restores the `v1.67.1` wasm build templates and build configuration, enforces the exact CLI in the fidelity harness, and can build both full and lite wasm artifacts. The lite fidelity gate now passes for Nautilus, DeepBook, and Apps/Kiosk against exact `sui 1.67.1-4e8aa9ee8b30`; DeepTrade remains an explicitly non-release-blocking investigation fixture.

The comparison range used for the upgrade change list is:

- previous Sui upgrade commit: `004ac62` (`Upgrade to Sui v1.63.3 and improve dependency resolution`)
- Sui `1.67.1` upgrade commit: `230014d` (`Upgrade Sui toolchain to 1.67.1`)

The exact Rust Sui baseline for all future parity work must be:

- Sui version: `1.67.1`
- Sui commit: `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93`
- observed exact CLI version: `sui 1.67.1-4e8aa9ee8b30`

Do not use the machine-local `sui` binary on `PATH` as the parity oracle unless it reports that exact version. During this investigation, `PATH` resolved to `sui 1.68.0-16bf4d124ac5`, which is not suitable for 1.67.1 verification.

## Issue Summary

### 1. Current Branch State Does Not Yet Represent A Clean 1.67.1 Upgrade

The historical upgrade work exists at commit `230014d`, but the current worktree does not currently show the full `1.67.1` upgrade as active project state. For example, `sui-version.json` in the current branch has been observed still pointing at the previous `1.63.3` commit in earlier checks, while the branch name suggests `1.67.1`.

Impact:

- tests can appear to target 1.67.1 while actually using 1.63.3 framework sources
- generated docs, lockfiles, and fixture outputs can be mixed across versions
- regressions are hard to classify because the codebase and baseline are not aligned

Required resolution:

- reconcile the current branch with the intended `230014d` upgrade state
- make `sui-version.json` the single source of truth for both build and resolver defaults
- add a test or preflight check that fails if `sui-version.json` and the exact Rust CLI baseline disagree

### 2. Exact Rust Sui Version Was Not Originally Enforced

The test harness shells out to `sui`, which means it can silently use whatever binary is first on `PATH`.

Observed during investigation:

```text
sui 1.68.0-16bf4d124ac5
```

Required baseline:

```text
sui 1.67.1-4e8aa9ee8b30
```

Impact:

- bytecode, dependency resolution, lockfile migration, and package fetch behavior can differ across Sui versions
- any comparison against `1.68.0` or `1.67.2` is not a valid `1.67.1` parity signal

Required resolution:

- add a `SUI_CLI` environment variable or test config option
- require fidelity tests to invoke that exact binary
- have the test harness run `sui --version` and fail unless it matches `1.67.1-4e8aa9ee8b30`

### 3. Fresh Wasm Build Is Blocked By Cargo Resolution Drift

In a clean worktree at the historical `230014d` upgrade commit, `npm ci` and `npm run build:js` succeed, but `npm run build:wasm` fails before DeepBook-specific verification.

Observed failure:

```text
error: failed to select a version for the requirement `core2 = "^0.4.0"`
  version 0.4.0 is yanked
required by package `multihash v0.17.0`
required by package `multiaddr v0.17.0`
required by package `sui-proxy v0.0.2`
```

Impact:

- the historical upgrade is not reproducible from a fresh checkout today
- the wasm compiler cannot currently be rebuilt for verification without further dependency work

Required resolution:

- determine why `sui-proxy` remains in the wasm workspace closure
- either remove/hollow out `sui-proxy` for the wasm build or patch the `multiaddr`/`multihash`/`core2` chain to a resolvable set
- stop deleting useful upstream lockfiles unless re-resolution is intentional and fully pinned
- commit a reproducible Cargo resolution strategy for the wasm build

Implementation status:

- `sui-proxy` is now hollowed out of the wasm build closure, which removes the yanked `core2` blocker.
- `clear_on_drop 0.2.5` is patched to a wasm-safe local stub so the build no longer requires host `clang` for its C helper.
- `wasm-bindgen-cli` is pinned to `0.2.120`, matching the schema emitted by the Rust dependency graph.
- `npm run build:wasm` now completes and writes both full and lite wasm artifacts.

### 4. DeepBook Fails Before Bytecode Comparison Under Exact 1.67.1 CLI

The exact Rust CLI was built from upstream commit `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93` and run against DeepBook commit `d3206b717c6f63593fae14d1ff9e1ec055f051bd`.

Default exact CLI run:

```text
INCLUDING DEPENDENCY MoveStdlib
INCLUDING DEPENDENCY Sui
INCLUDING DEPENDENCY token
BUILDING deepbook
Failed to fetch package MoveStdlib

Caused by:
    tcp connect error
```

After using local git remapping to avoid network transport noise, the exact CLI progressed further but still failed before compilation:

```text
INCLUDING DEPENDENCY MoveStdlib
INCLUDING DEPENDENCY Sui
INCLUDING DEPENDENCY token
BUILDING deepbook
Failed to fetch package token

Caused by:
    Object 0xdeeb7a4662eec9f2f3def03fb937a663dddaa2e215b8078a284d026b7946c270 not found
```

Impact:

- DeepBook does not currently produce a Rust CLI bytecode dump under exact 1.67.1 in this environment
- without Rust CLI bytecode output, wasm-vs-Rust bytecode parity cannot be honestly claimed

Required resolution:

- clean or regenerate the DeepBook fixture so the exact Rust CLI reaches compilation
- only compare wasm output after the exact Rust CLI successfully emits bytecode

Implementation status:

- The fidelity harness now invokes the exact CLI with `--dump-bytecode-as-base64 --no-tree-shaking`, which avoids RPC object lookups during bytecode dump generation.
- With local Sui git remapping enabled via `SUI_REPO_OVERRIDE`, exact CLI bytecode generation now succeeds for DeepBook.
- DeepBook now matches wasm output for modules, dependencies, and package digest in `npm run test:lite`.

### 5. DeepBook Fixture Lockfiles Pin Older Or Unreproducible State

The checked-in DeepBook root lockfile pins framework dependencies to Sui revision `22f9fc9781732d651e18384c9a8eb1dabddf73a6`, not the `1.67.1` revision `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93`.

With the root `Move.lock` present, the project resolver selects:

- `MoveStdlib` at `22f9fc9781732d651e18384c9a8eb1dabddf73a6`
- `Sui` at `22f9fc9781732d651e18384c9a8eb1dabddf73a6`
- `token` at `5e82e2dd1ea7d47957855ddc66f835585d6fe091`

With the root `Move.lock` removed, the resolver selects:

- `MoveStdlib` at `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93`
- `Sui` at `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93`
- `token` at `0a58db9702bf963c912af5e3d1544ae56aaed0eb`

The nested `packages/token/Move.lock` also carries published package metadata for:

```text
0xdeeb7a4662eec9f2f3def03fb937a663dddaa2e215b8078a284d026b7946c270
```

That is the same object the exact Rust CLI fails to fetch.

Impact:

- DeepBook is not a clean exact-1.67.1 fixture when existing locks are honored
- deleting only the root lock is insufficient because nested package locks can still inject stale published object state

Required resolution:

- regenerate DeepBook and token lockfiles under exact `sui 1.67.1-4e8aa9ee8b30`
- verify all framework packages resolve to `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93`
- remove or replace stale published object metadata that cannot be resolved in the test environment

### 6. DeepTrade Is Also Not A Clean Parity Fixture

The earlier 1.67.1 investigation found that DeepTrade fails differently in the wasm path and the Rust CLI path.

Wasm path representative failure:

```text
Could not resolve the name 'Pool'
Could not resolve the name 'Coin'
Unbound type 'Clock'
Could not resolve the name 'coin'
Could not resolve the name 'event'
```

Rust CLI path representative failure:

```text
Failed to fetch package Pyth

Caused by:
    Object 0x04e20ddf36af412a4096f9014f4a565af9e812db9a05cc40254846cf6ed0ad91 not found
```

Impact:

- DeepTrade does not currently provide a trustworthy parity signal
- the wasm and Rust paths fail at different stages, so the result is not a like-for-like compiler comparison

Required resolution:

- either make the DeepTrade fixture reproducible under exact 1.67.1 or remove it from the release-blocking fidelity set
- if kept, regenerate its lock and published metadata in a controlled environment and verify the exact Rust CLI reaches bytecode output first

Implementation status:

- DeepTrade is now marked as an investigation fixture in the harness and skipped for exact CLI parity by default.
- Its wasm build and transaction comparison still run, but it is not counted as a release-blocking wasm-vs-CLI oracle until the Pyth/Wormhole/deepbook lock graph is repaired.

### 7. Fidelity Harness Can Still Be Made Stricter

The fidelity harness was improved in the historical upgrade range, but it still needs stronger guardrails for exact-version verification.

Impact:

- cached CLI dumps can be stale across Sui versions
- generated lockfiles can be compared against fixture state from the wrong baseline
- network failures and published-object failures can be mistaken for compiler regressions

Required resolution:

- record the exact `sui --version` alongside every CLI dump
- invalidate cached dumps when the exact Sui version changes
- restore fixture lockfiles after CLI runs
- classify failures by stage: source fetch, published object fetch, dependency resolution, compilation, bytecode comparison, digest comparison, lockfile comparison

Implementation status:

- The harness now requires `SUI_CLI` to report `sui 1.67.1-4e8aa9ee*`.
- CLI dump caches include the exact CLI version and dump mode in their cache key and metadata.
- CLI runs restore `Move.lock` after execution.
- Generated fixture artifacts such as `MoveV4.lock`, `Move.lock.after_cli`, and `cli_dump_*.json` are excluded when cached fixture source files are read.
- `SUI_REPO_OVERRIDE` and `SUI_CLI_GIT_REWRITES` allow exact CLI runs to use local git checkouts without mutating global git config.

### 8. Lint Is Not Yet Clean

The historical investigation recorded existing lint issues in [test/integration/transactionAnalyzer.mjs](../test/integration/transactionAnalyzer.mjs).

Impact:

- lint cannot currently serve as a green release gate unless those issues are fixed or explicitly quarantined

Required resolution:

- fix the lint errors in the transaction analyzer
- include `npm run lint` in the final release verification matrix

## Remediation Plan

### Phase 1: Reconcile The Upgrade Branch

1. Decide whether `230014d` is the canonical starting point for the 1.67.1 upgrade.
2. Reapply or merge the complete 1.67.1 upgrade state into the active branch.
3. Confirm these files reflect 1.67.1 consistently:
   - [sui-version.json](../sui-version.json)
   - [scripts/build-config.json](../scripts/build-config.json)
   - [scripts/build-wasm.mjs](../scripts/build-wasm.mjs)
   - `scripts/templates/v1.67.1/`
   - [sui-move-wasm/Cargo.toml](../sui-move-wasm/Cargo.toml)
4. Keep unrelated working tree changes, such as the current [.gitignore](../.gitignore) edit, separate from the upgrade work unless they are intentionally part of the fix.

Exit criteria:

- `sui-version.json` points at `1.67.1` and `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93`
- the active branch contains the 1.67.1 build templates and wasm crate changes
- no unrelated file edits are mixed into the upgrade patch

### Phase 2: Make The Rust Baseline Exact And Repeatable

1. Build the exact Rust CLI from upstream Sui commit `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93`.
2. Store or configure the resulting binary path, for example via `SUI_CLI=/path/to/sui`.
3. Update the fidelity harness to use `SUI_CLI` instead of bare `sui`.
4. Add a preflight assertion:

```text
sui --version == sui 1.67.1-4e8aa9ee8b30
```

Exit criteria:

- every CLI comparison logs the exact Sui binary path and version
- tests fail early if the exact version is not available

### Phase 3: Restore A Reproducible Wasm Build

1. Investigate why `sui-proxy` remains reachable in the wasm build dependency graph.
2. Prefer removing or hollowing out non-wasm runtime crates that are not needed by `sui-move-wasm`.
3. If removal is not enough, patch the `multiaddr`/`multihash`/`core2` chain using the centralized [scripts/build-config.json](../scripts/build-config.json) strategy.
4. Avoid deleting upstream `Cargo.lock` files unless the replacement resolution is fully pinned and reproducible.
5. Re-run:

```bash
npm run build:wasm
npm run build:js
npm run typecheck
```

Exit criteria:

- fresh checkout can run `npm ci && npm run build` without yanked-crate failures
- wasm artifacts are generated for both full and lite builds

### Phase 4: Repair DeepBook As A Fidelity Fixture

1. Start with the exact DeepBook source commit used by the fidelity test: `d3206b717c6f63593fae14d1ff9e1ec055f051bd`.
2. Remove or regenerate both root and nested lockfiles under exact `sui 1.67.1-4e8aa9ee8b30`:
   - `packages/deepbook/Move.lock`
   - `packages/token/Move.lock`
3. Verify the regenerated graph uses `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93` for `MoveStdlib` and `Sui`.
4. Ensure the fixture no longer depends on unavailable published object `0xdeeb7a4662eec9f2f3def03fb937a663dddaa2e215b8078a284d026b7946c270` unless the test environment can fetch it reliably.
5. Run the exact Rust CLI first:

```bash
$SUI_CLI move build --dump-bytecode-as-base64 -e mainnet
```

6. Only after the exact Rust CLI emits bytecode, run the wasm builder and compare modules, dependencies, digest, and generated lockfile.

Exit criteria:

- exact Rust CLI produces a DeepBook bytecode dump
- wasm builder produces DeepBook output from the same source graph
- module bytecode, dependency IDs, package digest, and lockfile data either match exactly or have documented, intentional differences

### Phase 5: Decide The Fate Of DeepTrade

1. Treat DeepTrade as non-authoritative until exact Rust CLI reaches bytecode output.
2. Either repair its published dependency state or move it to a non-release-blocking investigation suite.
3. If kept as a release blocker, regenerate its fixture under exact 1.67.1 and ensure `Pyth`, `deepbook`, `multisig`, and framework dependencies are all reproducible.

Exit criteria:

- DeepTrade either passes exact CLI and wasm parity, or it is explicitly excluded from release-blocking fidelity tests with rationale

### Phase 6: Harden The Fidelity Harness

1. Add stage-aware error reporting:
   - exact CLI version check
   - source fetch
   - published object fetch
   - dependency graph resolution
   - compilation
   - bytecode comparison
   - digest comparison
   - lockfile comparison
2. Save CLI dumps with metadata:
   - Sui binary path
   - `sui --version`
   - package commit
   - package path
   - network
   - generated lockfile hash
3. Invalidate cached CLI dumps when any metadata changes.
4. Ensure CLI runs cannot permanently mutate checked-in fixture locks.

Exit criteria:

- a failing fidelity test clearly says whether the problem is environment, fetch, lockfile, compiler, digest, or bytecode parity
- reruns are deterministic from a clean checkout

### Phase 7: Final Verification Matrix

Before declaring Sui 1.67.1 fully working and verified, run this matrix from a clean checkout:

```bash
npm ci
npm run build:wasm
npm run build:js
npm run typecheck
npm run lint
SUI_CLI=/path/to/exact/sui-1.67.1 npm run test:lite
SUI_CLI=/path/to/exact/sui-1.67.1 npm run test:integration
```

Required package-level parity results:

- Nautilus passes bytecode, dependencies, digest, and lockfile comparison
- DeepBook passes bytecode, dependencies, digest, and lockfile comparison
- Apps/Kiosk passes bytecode, dependencies, digest, and lockfile comparison, if retained in the suite
- DeepTrade passes or is explicitly removed from the release-blocking suite

## Definition Of Done

The Sui 1.67.1 upgrade should be considered complete only when all of the following are true:

- the active branch consistently pins Sui `1.67.1` at `4e8aa9ee8b307b294cc85baf7d08af1f432e3d93`
- the wasm build is reproducible from a clean checkout
- the fidelity harness refuses to compare against the wrong Sui CLI version
- DeepBook is regenerated or repaired as a clean exact-1.67.1 fixture
- exact Rust CLI output exists for every release-blocking fixture
- wasm output matches exact Rust CLI output for modules, dependencies, digest, and lockfile behavior
- `npm run build`, `npm run typecheck`, `npm run lint`, `npm run test:lite`, and `npm run test:integration` all pass from a clean checkout
